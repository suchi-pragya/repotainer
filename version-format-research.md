# Version formats and resolution research

Research for the Repotainer EGM brainstorm, 2026-11-22. The [Mise registry](https://mise.jdx.dev/registry.html#tools) served as a sample of tools and installation backends. Upstream specifications and release records supply the comparison rules. This sample covers distinct cases across the registry and beyond it.

## What a version can contain

`A.B.C` describes the shape of a string. The tool or ecosystem defines what the components mean, how versions sort, and what compatibility promises apply. The same string can also represent a release, a prefix, or a range depending on the field it came from.

| Scheme | Examples | What the comparator needs to know |
| --- | --- | --- |
| Semantic Versioning | `1.2.3`, `1.2.3-alpha.1`, `1.2.3-rc.2+build.9` | Compare major, minor, and patch numerically. A prerelease sorts below its corresponding final release. Compare prerelease identifiers using SemVer rules. Build metadata has no effect on precedence, so retain the original identifier for an exact artifact request. An ecosystem can add constraints and prerelease eligibility rules. [SemVer specification](https://semver.org/) · [npm range rules](https://github.com/npm/node-semver#ranges) |
| Python packaging (PEP 440) | `3.14.0a1`, `3.14.0b1`, `3.14.0rc1`, `3.14.0`; package versions may also use `1!2.0`, `2.0.dev1`, `2.0.post1`, or `2.0+local.1` | The scheme defines epochs, numeric release segments, prerelease, post-release, development, and local segments. Its ordering and matching rules differ from SemVer. Use them for `requires-python`. Interpret `.python-version` according to the supported request format, where `3.12` can mean any patch in the 3.12 series. [Python version specifiers](https://packaging.python.org/en/latest/specifications/version-specifiers/) · [uv version requests](https://docs.astral.sh/uv/concepts/python-versions/#python-version-files) |
| Calendar versions | yt-dlp `2025.03.31`, Ubuntu `24.04` | Interpret date components and any same-period suffix according to the project. Zero-padded dates can be meaningful and the date says nothing about compatibility. A date-like image tag can still be a moving target. [Calendar Versioning](https://calver.org/) · [yt-dlp release](https://github.com/yt-dlp/yt-dlp/releases/tag/2025.03.31) · [Docker image tags](https://docs.docker.com/reference/cli/docker/image/pull/) |
| Tool-specific numeric versions | PostgreSQL `16.2`, Chromium `MAJOR.MINOR.BUILD.PATCH`, uv `0.x.y` | PostgreSQL changed from three components to two starting at 10. Chromium uses four components. uv assigns breaking changes to minor increments under its current policy. Dotted versions need the tool's numbering and compatibility rules. [PostgreSQL version policy](https://www.postgresql.org/support/versioning/) · [Chromium version numbers](https://www.chromium.org/developers/version-numbers/) · [uv version policy](https://docs.astral.sh/uv/reference/policies/versioning/) |
| Toolchain-specific ordering | Go `1.21`, `1.21rc1`, `1.21.0`; Java `25-ea+15` | Go sorts `1.21 < 1.21rc1 < 1.21.0`. Before Go 1.21, the two-component form could be the initial stable release. Java has its own rules for its numeric components, prerelease identifiers, build numbers, and optional information. [Go toolchain versions](https://go.dev/doc/toolchain#version) · [Java Runtime.Version](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Runtime.Version.html) |
| Distribution package versions | Debian shape `[epoch:]upstream_version[-debian_revision]` | A distribution revision identifies a packaged build. Debian uses its own comparison rules, including special ordering for `~`. The distribution version and upstream release have different identities. [Debian Policy Manual](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version) |

## Values that select versions or artifacts

| Kind | Examples | How to handle it |
| --- | --- | --- |
| Exact release, prefix, or range | `3.12.8`, `3.12`, `>=3.12.5,<3.13`, `^1.2.3` | Determine what the source field means before comparing. `1.2.3` can be an exact release in Mise and a compatible range in a Cargo dependency declaration. Python and npm have different range grammars. [Mise version requests](https://mise.jdx.dev/dev-tools/versions.html) · [Cargo dependency requirements](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#version-requirement-syntax) · [npm range rules](https://github.com/npm/node-semver#ranges) |
| Alias or release channel | `latest`, `lts`, `stable`, `beta`, `nightly` | Resolve through the relevant ecosystem or backend before comparing to a numbered release. An explicit channel carries intent, even if it currently points at the same version as a numeric request. [Mise version requests](https://mise.jdx.dev/dev-tools/versions.html) · [npm distribution tags](https://docs.npmjs.com/cli/v11/commands/npm-dist-tag/) · [Rust release channels](https://doc.rust-lang.org/book/appendix-07-nightly-rust.html) |
| Source or artifact reference | Git tag, branch, commit, package URL, image digest | A reference may identify a published release, a moving branch, or an exact artifact. Compare verified artifact identities for equality. Ordering requires a scheme or metadata that ties those references to releases. Mise reference support varies by backend. [Mise Git references](https://mise.jdx.dev/dev-tools/versions.html) · [Docker digests](https://docs.docker.com/reference/cli/docker/image/pull/) |

A prerelease can be published and installable while still being unsuitable as the default. A development build may likewise be published, while a source checkout may have no published artifact. Keep release stage and availability separate from version ordering. [Zig releases and development builds](https://ziglang.org/download/) · [Go toolchain versions](https://go.dev/doc/toolchain#version)

## What this means for Repotainer

1. **Extract evidence with its meaning intact.** Keep the tool identity, project scope, source path, field, and raw value. `package.json`'s `version` describes the package itself, while `engines.node` describes its Node requirement. `pyproject.toml`'s `project.requires-python` describes Python compatibility. The JSON or TOML reader gets the string. A rule for the field tells the resolver how to interpret it. [npm package.json reference](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/) · [Python packaging guide](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)
2. **Compare with the applicable scheme across the selected scan.** Give the resolver one common way to ask whether a candidate satisfies a declaration, backed by the ecosystem's own parser and ordering rules. Treat exact releases, prefixes, and ranges as sets of possible candidates. Consider every declaration the inventory and detector surface for the same tool, including nested packages and examples. The selected scan root controls the scope. [Scan-root behavior](docs/designs/repository-inventory.md#choose-the-scan-root)
3. **Preserve a compatible exact version or derive the lowest stable candidate.** If a repository supplies an exact request and all applicable declarations accept it, use that version. When only a range or overlapping constraints remain, use the lowest stable candidate the scheme can determine. For `.python-version` containing `3.12` and `requires-python = ">=3.12.5,<3.13,!=3.12.5"`, `3.12.6` is the first eligible patch by number. Mise can attempt installation in the Dev Container. The numeric candidate alone does not verify release availability. [Mise version requests](https://mise.jdx.dev/dev-tools/versions.html)
4. **Apply source precedence when declarations conflict.** Assign a deliberate priority to each version evidence source for the tool. When the declarations cannot all be satisfied, use the highest-priority evidence to guide the choice and report which evidence was overridden. For Python in one project, the user's proposed order puts `pyproject.toml`'s `project.requires-python` above `.python-version` because it declares the compatibility boundary. A malformed or unsupported declaration needs a diagnostic. Use `latest` when the tool is detected with no version evidence.
5. **Translate the result into a Mise request.** Pass a selected release using the backend's accepted spelling. Retain the upstream version for comparison and the backend identifier for installation where those differ. A constraint such as `^24` cannot generally be copied into `mise.toml`, and a floating prefix can choose a different release later. [Mise version requests](https://mise.jdx.dev/dev-tools/versions.html) · [Mise backend selection](https://mise.jdx.dev/dev-tools/backend_architecture.html)

## Python examples

| `.python-version` | `requires-python` | Result under the proposed rules |
| --- | --- | --- |
| `3.12.8` | `>=3.12.5,<3.13` | Request `3.12.8`. The exact request satisfies the range. |
| `3.12` | `>=3.12.5,<3.13` | Request `3.12.5`. It is the lowest stable candidate in the overlap. |
| Absent | `>=3.13,<3.14` | Request `3.13.0`. It is the lowest stable candidate in the range. |
| `3.12.8` | `>=3.13,<3.14` | Request `3.13.0` and report that `pyproject.toml` took precedence over `.python-version`. |
| Absent | Absent | Use `latest` if other evidence identifies Python. |

## When source priority cannot break a tie

Suppose `my-app/pyproject.toml` declares `>=3.13,<3.14` and `my-app/examples/legacy/pyproject.toml` declares `>=3.12,<3.13`. A scan of `my-app` sees two equally ranked, disjoint requirements. The root manifest's location gives it no extra priority. A scan of `my-app/examples/legacy` sees only its own requirement in this example and requests `3.12.0`. If the legacy requirement were `>=3.12,<3.14`, a root scan could choose `3.13.0` from the overlap without prompting.

For an interactive run, show a numbered menu with one option per candidate derived from the conflicting evidence. Label each option with the candidate version, source path, field, and declared value. Put `latest` last. In the root scan above, the choices are `3.13.0` from `pyproject.toml`, `3.12.0` from `examples/legacy/pyproject.toml`, and `latest`. Wait for a valid selection before writing scaffold files, then use the selected request.

For an unattended run, report the conflicting declarations and write `latest` for the affected tool. The message should make clear that `latest` is the fallback and that the declarations remain incompatible. Ranges whose minimum cannot be derived from a supported scheme are a separate open case.

## Mise integration on the host

Repotainer generates `mise.toml` from repository evidence. The generated Dev Container runs `mise install` during setup. A supported host-side version comparison can produce a concrete request without requiring a host Mise installation, network lookup, or GitHub credentials. A release catalog would help if Repotainer later needs to search published versions, for example to recover when a derived candidate is unavailable for the target. [Current Mise design](docs/designs/mise-tool-configuration.md#render-and-write) · [Mise remote version listings](https://mise.jdx.dev/cli/ls-remote.html)

Mise ships a Rust library used by its CLI and explicitly marks that library as outside its public API. The npm package distributes the binary. The plugin interface extends a running Mise installation. No supported embeddable resolver or official Python SDK was found in the upstream interfaces checked. [Mise Cargo manifest](https://github.com/jdx/mise/blob/main/Cargo.toml) · [Mise installation docs](https://mise.jdx.dev/installing-mise.html#npm) · [Mise plugin docs](https://mise.jdx.dev/plugins.html)

The hosted `mise-versions` service caches registry tool versions and public GitHub data. Mise uses it to reduce anonymous GitHub rate-limit pressure and can fall back to GitHub or the tool's source. The public site and project repository checked here do not document a supported third-party resolver API. Its cached data and fallback behavior also differ from what every backend can install. [Mise versions service](https://mise-versions.jdx.dev/) · [Mise versions source](https://github.com/jdx/mise-versions) · [Mise cache and fallback settings](https://mise.jdx.dev/configuration/settings.html#use_versions_host)

The proposed first implementation would use Python to test this interface because Repotainer already detects both Python declarations. Keep Go, npm, calendar versions, and opaque references as design examples. Use each additional scheme when a detector needs it and its behavior can be verified. This research checked documented formats and examples. It did not query live version lists or install sample tools.
